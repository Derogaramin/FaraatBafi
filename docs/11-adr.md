# ثبت تصمیم‌های معماری (ADR)

هر تصمیم بزرگ فنی با شماره، وضعیت، زمینه و پیامدها ثبت می‌شود.
این سند طبق نقشهٔ راه (`docs/10-roadmap.md` §۱۳) نگه‌داری می‌شود.

---

## ADR-001 — باقی‌ماندن بر هستهٔ دست‌ساز (عدم مهاجرت به فریم‌ورک)

- **وضعیت**: پذیرفته‌شده (۱۴۰۵/۰۷) • بازنگری: پس از فاز ۳ اگر تیم > ۴ نفر شد
- **زمینه**: سامانه با هستهٔ سبک داخلی (Router/Model/View/Auth/Events) نوشته شده.
  گزینه‌ها: مهاجرت به Laravel/Symfony یا ادامهٔ هستهٔ داخلی با تقویت تدریجی.
- **تصمیم**: ادامهٔ هستهٔ داخلی.
- **دلایل**: کنترل کامل بر FUCS و تقویم شمسی؛ حجم کم (بدون ~۴۰MB وابستگی)؛
  انطباق کامل با نیاز تعاونی در مقیاس فعلی؛ هزینهٔ مهاجرت (بازنویسی ۲۰۰+ فایل) > منفعت.
- **پیامدها**: مسئولیت نگهداری هسته با تیم است → با تست‌های واحد هسته (Router/Validator/Jalali/…)
  و مستندسازی `docs/02` مدیریت می‌شود. نبود اکوسیستم (ORM, Queue, …) با معادل‌های داخلی
  سبک (QueryBuilder, QueueWorker جدول‌محور) پوشش داده می‌شود.

## ADR-002 — صف رویدادها جدول‌محور (نه Redis) در فاز ۰

- **وضعیت**: پذیرفته‌شده • ارتقا: Redis در فاز ۲ با همان API
- **زمینه**: شنونده‌های سنگین (SMS، آمار) درخواست HTTP را کند و شکننده می‌کنند.
- **تصمیم**: جدول `event_queue` + کارگر `php bin/faraat queue:work` (cron یا daemon).
- **دلایل**: وابستگی زیرساختی جدید صفر؛ روی shared hosting هم کار می‌کند؛
  retry (۳ تلاش) و ستون last_error داخلی است.
- **پیامدها**: payload رویدادهای صف‌شده باید **سریال‌شدنی** باشد (id/code نه آبجکت)؛
  تأخیر پردازش در حد فاصلهٔ cron است (برای SMS قابل قبول).
  رویدادهای صف‌شده در `config/app.php → queued_events` فهرست می‌شوند (پیش‌فرض: خالی = همگام).

## ADR-003 — Enumهای رشته‌ای PHP برای وضعیت‌ها

- **وضعیت**: اجرا شده (۱۴۰۵/۰۷)
- **زمینه**: وضعیت‌های سفارش/تولید به‌صورت رشتهٔ خام در ۲۰+ فایل تکرار می‌شدند
  (نقد §۳٫۳)؛ ماشین حالت سفارش در سه نقطه پخش بود (نقد §۱۰).
- **تصمیم**: `Core\Enums\OrderStatus` و `Core\Enums\WorkOrderStatus` به‌عنوان
  **منبع حقیقت** (برچسب، رنگ، گذارهای مجاز، ستون زمانی). `Core\Statuses` به نمای
  سازگار برای ویوها تبدیل شد. `Core\Business\OrderFlow` تنها نقطهٔ تغییر وضعیت سفارش.
- **پیامدها**: ویوها فعلاً با رشته کار می‌کنند (سازگاری)؛ کد جدید باید از
  `OrderStatus::tryFrom()` استفاده کند. مهاجرت کامل ویوها به enum در فاز ۱٫۵ ادامه دارد.

## ADR-004 — ممیزی فیلدمحور با فراخوانی صریح در مرز سرویس‌ها

- **وضعیت**: اجرا شده (۱۴۰۵/۰۷)
- **زمینه**: تغییر قیمت/موجودی/نرخ‌ها بدون ردپا بود (نقد §۶٫۱).
  گزینه‌ها: trigger در DB، middleware روی Model::save، یا فراخوانی صریح.
- **تصمیم**: `Core\Audit::log/diff` در نقاط تغییر حساس (واریانت، ماده، بافنده،
  نمایندگی، وضعیت سفارش) + جدول `field_audits` + صفحهٔ `/admin/audits`.
- **دلایل**: triggerها از PHP و تست بیرون می‌افتند؛ hook خودکار روی save هنوز
  زمینه (کد FUCS موجودیت) را نمی‌داند؛ فراخوانی صریح خوانا و تست‌پذیر است.
- **پیامدها**: هر نقطهٔ نوشتاری جدیدِ حساس باید Audit صدا بزند (چک‌لیست code review).

## ADR-005 — Polling به‌جای SSE/WebSocket برای اعلان‌ها (فعلاً)

- **وضعیت**: پذیرفته‌شده موقت • بازنگری: پایان فاز ۱
- **زمینه**: نقشهٔ راه SSE را پیشنهاد داده بود؛ اما سرور توسعهٔ PHP تک‌رخنه‌ای
  با اتصال بازِ SSE بقیهٔ درخواست‌ها را مسدود می‌کند.
- **تصمیم**: polling سبک ۳۰ ثانیه‌ای روی `GET /notifications/unread-count`
  (پاسخ ~۱۰۰ بایت) + endpoint آماده برای ارتقا.
- **پیامدها**: تأخیر اعلان ≤ ۳۰ ثانیه (قابل قبول برای تعاونی)؛ مصرف شبکه ناچیز.
  مسیر ارتقا: `PHP_CLI_SERVER_WORKERS>1` یا nginx+FPM (در docker-compose موجود است)
  سپس افزودن `/notifications/stream` با `text/event-stream`.

## ADR-006 — WebP تنها قالب خروجی آپلود

- **وضعیت**: اجرا شده (۱۴۰۵/۰۷)
- **زمینه**: تصاویر ارسالی مدیران ۲ تا ۸ مگابایت JPEG/PNG بود (نقد §۵٫۴).
- **تصمیم**: `Upload::image` همهٔ ورودی‌ها را به WebP (کیفیت ۸۲، حداکثر عرض ۱۴۰۰px)
  تبدیل می‌کند؛ SVG **کاملاً حذف** شد (ریسک Stored XSS — نقد S1).
- **پیامدها**: ~۷۰٪ کاهش حجم؛ پشتیبانی مرورگر ≥۹۶٪؛ در صورت نبود GD،
  fallback به ذخیرهٔ فایل اصلی با پسوند خودش.

## ADR-007 — منطقهٔ زمانی نشست پایگاه داده هم‌تراز با PHP

- **وضعیت**: اجرا شده (۱۴۰۵/۰۷) — رفع باگ واقعی
- **زمینه**: MariaDB روی UTC و PHP روی Asia/Tehran بود؛ هر مقایسهٔ
  «PHP date در برابر SQL NOW()» (مثل پنجرهٔ ۱۵ دقیقه‌ای Throttle یا KPI امروز)
  ۳٫۵ ساعت خطا داشت و در تست‌ها کشف شد.
- **تصمیم**: در `Database::connection()` بلافاصله
  `SET time_zone = '<offset>'` از منطقهٔ زمانی PHP اجرا می‌شود.
- **پیامدها**: همهٔ مقایسه‌های زمانی سازگار شد؛ استقرار باید `date_default_timezone_set`
  را از config بگیرد (هم‌اکنون Asia/Tehran). دادهٔ تاریخی seed با فرض زمان تهران بازسازی شد.

## ADR-008 — 2FA فقط برای «عملیات حساس» نقش M (نه کل ورود)

- **وضعیت**: اجرا شده (۱۴۰۵/۰۷)
- **زمینه**: نقش M به مالی و حاکمیت دسترسی دارد (نقد S7)؛ اجبار 2FA روی *ورود*
  همهٔ اعضا، اصطکاک زیاد و ریسک lockout در تعاونی کوچک است.
- **تصمیم**: TOTP اختیاری برای ثبت‌نام؛ اما **POSTهای حساس** (اسناد مالی، پورسانت،
  جلسات/مصوبات/رأی، تنظیمات) با میان‌افزار `2fa` محافظت می‌شوند:
  کاربر ثبت‌نام‌نکرده → هدایت به `/admin/security`؛ ثبت‌نام‌کرده → تأیید کد در نشست.
- **پیامدها**: GETها سریع می‌مانند؛ سطح محافظت دقیقاً جایی است که پول/حاکمیت جابه‌جا می‌شود.
  فهرست نقاط حساس در `config/auth.php → require_2fa_for` و route های `['csrf','2fa']`.

## ADR-009 — محدودسازی نرخ ورود دو‌آستانه‌ای (شناسه / IP)

- **وضعیت**: اجرا شده (۱۴۰۵/۰۷)
- **تصمیم**: ۵ شکست برای هر **شناسه** → ۱۵ دقیقه قفل همان شناسه؛
  ۲۰ شکست برای هر **IP** → قفل IP (محافظت در برابر اسپری).
  ورود موفق، شکست‌های همان شناسه را پاک می‌کند.
- **دلایل**: آستانهٔ IP برابر با شناسه، کاربران پشت NAT یک دفتر را دسته‌جمعی قفل می‌کرد.
- **پیامدها**: پیام قفل عمدداً مبهم است تا شمارنده لو نرود؛ صفحهٔ «امنیت حساب»
  تاریخچهٔ تلاش‌ها را به خود کاربر نشان می‌دهد.
